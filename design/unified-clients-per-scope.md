# Unified clients, final: one `clients/` per scope, same shape everywhere

> **Status: implemented, verified end to end.** Supersedes the layout halves of
> [`unified-clients-option-c.md`](./unified-clients-option-c.md) (packages
> directly in the scope / at the module root) and
> [`unified-clients-shared-core.md`](./unified-clients-shared-core.md) (one
> workspace-level `.dagger/core`). Option C's principle — the package manifest
> is the only link — stands unchanged; what moved is where packages live.

## 1. The layout: one rule, no exceptions

Every scope that has clients has a `clients/` directory, holding one
self-contained npm package per client and the scope's own `@dagger.io/dagger`
package beside them. A module scope and a client-only scope generate the
identical shape; the packages install and run anywhere.

```
<scope>/clients/
  dagger/            @dagger.io/dagger — bundle + core bindings, real package
  <name>/            @dagger.io/<name> — <name>.gen.ts + package.json
  loader.gen.ts      module scopes only: the entrypoint object loader
```

Each client package depends on `file:../dagger` and `file:../<sibling>`, so
installing one pulls everything it references. The core package carries
`main`/`types`/`exports`, so it resolves under any moduleResolution setting.

## 2. A module scope

```
$ dagger module init typescript --entrypoint -n test
```

```
.dagger/modules/test/
  package.json                "@dagger.io/dagger": "file:./clients/dagger"
  tsconfig.json               experimentalDecorators only — no path aliases
  src/index.ts
  clients/dagger/             the module's own core package
  clients/test/               the self client, generated by default
  clients/loader.gen.ts
  __dagger.dispatch.ts  entrypoint/main.dang  dagger-module.toml
```

- **Core is installed by default**: the one `@dagger.io/*` dep a fresh module
  carries. `npm install` once and the editor resolves everything — package.json
  is the resolver, the tsconfig carries no aliases.
- **The self client is generated, not wired.** `npm install ./clients/test`
  opts in; the dep then survives regeneration (keep-only). `dagger module
  client add .` records it in `dagger.toml` (as the resolved path) and wires
  the dep by default — allowed by dagger/dagger#14188, which stops the
  generation graph from reading a scope's own module as a self-cycle.
- **A declared client** (`dagger module client add <ref>`) lands at
  `clients/<name>/` and is wired as `file:./clients/<name>`.
- The loader imports each client **relatively** (`./test/test.gen.js`), so an
  uninstalled self client still resolves at dispatch time; core stays a bare
  import, resolved through the default install.

The recipe's install context is the manifest plus `clients/**` — the file:
targets ride with the manifest, so a source edit reinstalls nothing, and npm's
relative symlinks resolve identically under the runtime's workspace mount.

## 3. A client-only scope

```
$ mkdir tools && cd tools && dagger module client add ../.dagger/modules/test
```

```
tools/
  package.json                @dagger.io/dagger + @dagger.io/test as file: deps
  clients/dagger/  clients/test/
```

`npm install`, then from the scope's own code:

```ts
import { connection, dag } from "@dagger.io/dagger"
import { test } from "@dagger.io/test"

await connection(async () => {
  console.log(await test(dag.currentWorkspace()).baseImageAddress())
})
```

run with `dagger run npx tsx main.ts`. Only the SDK's own `@dagger.io/*` deps
and the `clients/` directory are managed; everything else in the scope is the
user's. A dep the user pointed elsewhere — another scope's client, a registry —
is never touched.

## 4. What this replaced, and why

- **The workspace-level `.dagger/core`** (one vendored core per workspace) is
  gone. Per-scope copies cost duplication but buy uniformity and
  self-containment: a scope's packages resolve with no path that leaves the
  scope, which is also what makes them installable from anywhere and what a
  published `@dagger.io/dagger` later replaces wholesale (each `file:../dagger`
  becomes a version; the `dagger/` directories disappear). Old copies are
  pruned on regeneration.
- **Packages directly in the scope / at the module root** are gone; everything
  nests under `clients/`, which is fully generated and fully owned — pruning is
  "anything in clients/ this run did not render", with `node_modules` left
  alone.
- **The embedded `sdk/`** never comes back for entrypoint modules; `[runtime]`
  modules keep the legacy embedded layout untouched.

## 5. Verified

On a fresh workspace against the manifest-v2 engine (beta.14): init produces
the §2 layout and a call runs; `npm install ./clients/test` + a self-call
function + regenerate keeps the dep, stays byte-quiet, and `call self-call`
answers through the generated client; a client-only scope produces the §3
layout, and `dagger run npx tsx main.ts` reaches the module from plain user
code; `dagger module client add .` (dev engine with dagger/dagger#14188)
records the resolved path and generation stays quiet. codegen, config-updater
and the dang parse gate are green.
